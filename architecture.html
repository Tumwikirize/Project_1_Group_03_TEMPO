High-Level System Architecture

TEMPO architectural approach, component responsibilities, design rationale, and requirements traceability.

1. High-Level Architectural Overview

TEMPO uses a three-layer architecture consisting of a Presentation Layer, an Application Logic Layer, and a Data Persistence Layer. This approach separates the user interface from the processing and storage of activity, goal, and time-recording data. Each layer has a specific responsibility, allowing individual components to be developed and modified without requiring major changes to the rest of the system.

Presentation Layer - handles interactions between the user and TEMPO. It provides the dashboard, activity management screens, time logging forms, and progress reports described in the User Interface Design section. Users interact with this layer to create activities, set goals, record time, and review their progress. Rather than performing calculations or directly modifying stored data, the interface communicates with the appropriate application components. This layer also enables an opportunity to incorporate a scenario-based approach to the design requirements.

Application Logic Layer - contains the main functionality of TEMPO. It is divided into three primary functional areas: Activity and Goal Management, Time Logging, and Progress Tracking and Analytics. Activity and Goal Management handles the creation, modification, suspension, and archival of activities and their associated goals. Time Logging validates and manages individual time records. Progress Tracking and Analytics uses saved records and goal information to calculate totals, evaluate goal completion, and generate statistical summaries and projections. Separating these responsibilities allows each component to focus on a specific function while sharing the information necessary to support the overall system.

Data Persistence Layer - manages the storage and retrieval of activity information, goal configurations, and individual time records. This layer provides a common source of data for the application components. Time records are stored individually rather than as accumulated totals, allowing the system to recalculate progress when records are added, modified, or deleted. Historical goal configurations are also preserved so that changes to a user's current goal do not affect previously recorded progress.

1.1 Architectural Approach and Justification

A layered architecture was selected because TEMPO has several related functions that depend on the same underlying data but perform different responsibilities. For example, modifying a time entry requires the time logging component to validate and save the change, while the Analytics component must use the updated information to recalculate progress. Separating these operations reduces dependencies between components and helps maintain consistency throughout the system.

This approach also supports the modular design described in the other sections of the project. Activity and Goal Management, Time Logging, and Analytics can be designed and tested independently, provided they follow the established interfaces and data structures. Changes to the presentation of charts or reports, for example, should not require modifications to how time entries are stored or validated.

An alternative would be to combine the interface, calculations, and storage operations into a single component. Although this could simplify the initial design, it would create tighter dependencies between unrelated responsibilities. As TEMPO expands and/or more iterations are incorporated, modifying one feature could require changes across several others, making the system more difficult to maintain. The selected architecture provides a balance between simplicity and separation of responsibilities.

This architectural approach primarily supports NFR-01, which requires records to persist across sessions; NFR-02, which requires consistent time units and reporting periods; and NFR-06, which addresses responsiveness when generating reports. It also supports the functional requirements associated with activity management (FR-01 through FR-08), time recording (FR-09 through FR-13), and progress tracking (FR-14 through FR-20).

2.2 Component Interactions

The Presentation Layer provides the dashboard, activity management screens, time logging forms, and progress reports. User requests are directed to the appropriate application component.

The Application Logic Layer contains the Goal Manager (C-30), Time Logging Service (C-04), and Analytics Service (C-50), along with its supporting calculation components (C-51–C-56). These components manage user activities, process time entries, and generate progress reports.

The Data Persistence Layer maintains activity information, goal configurations, and individual time records. The Time Entry Repository (C-05) handles time records, while the Goal Manager coordinates activity and goal storage.

When users modify goals or time entries, the affected records are updated, and the Change Listener (C-56) notifies the Analytics Service to invalidate outdated reports. This separation ensures that calculations use current information without directly modifying stored records.

3. Component Communication and Design Rationale

3.1 Component Communication

TEMPO components communicate through the Application Logic Layer. User requests are routed from the Presentation Layer to the Goal Manager (C-30), Time Logging Service (C-04), or Analytics Service (C-50). These components retrieve or modify information through the Data Persistence Layer.

The Analytics Service uses stored goal configurations and time records to calculate progress and generate reports. When records change, the Change Listener (C-56) invalidates outdated analytics, ensuring subsequent calculations reflect the latest information.

5. External Dependencies

TEMPO is designed as a self-contained web application with no required third-party APIs. Its primary dependencies are a web browser for user interaction and persistent storage for maintaining activity, goal, and time records.
